可以。既然你们准备在**空项目**里实现，我建议阶段一目标不要定成“做一个能聊天的 Agent”，而是定成：

> **做出一个最小但边界正确的 Harness Runtime。**
>
> 它能够接收 Request，构造 Context，从 Registry 找到本地 Agent/Tool，经过 Policy 决策后执行，并完整产生 Trace。
>
> 业务能力只是插件，Harness Core 不知道任何具体业务。

阶段一甚至可以**先不做 LLM Planner、多 Agent 编排、Memory、Workflow、远程插件、数据库持久化**。先把骨架和 SPI 打稳。

# 一、阶段一最终应该长这样

```text
                   ┌─────────────────┐
                   │   Application   │
                   │  API / CLI/Test │
                   └────────┬────────┘
                            │
                         Request
                            │
                            ▼
                 ┌──────────────────────┐
                 │    Harness Runtime   │
                 │                      │
                 │ Request + Context    │
                 │ Invocation Pipeline  │
                 └───────┬──────────────┘
                         │
        ┌────────────────┼────────────────┐
        │                │                │
        ▼                ▼                ▼
 ┌─────────────┐  ┌─────────────┐  ┌─────────────┐
 │  Registry   │  │   Policy    │  │    Trace    │
 │             │  │             │  │             │
 │ Capability  │  │ Allow/Deny  │  │ Span/Event  │
 │ Discovery   │  │ Constraints │  │ Metrics     │
 └──────┬──────┘  └─────────────┘  └─────────────┘
        │
        │ resolve
        ▼
 ┌──────────────────────────────┐
 │         Plugin SPI           │
 │                              │
 │ Agent SPI      Tool SPI      │
 └───────┬────────────┬─────────┘
         │            │
         ▼            ▼
  Local Agent     Local Tool
   Plugins          Plugins
```

最关键的是依赖方向：

```text
业务 Plugin
     │
     ▼
Plugin SPI / Contracts
     ▲
     │
Harness Runtime
```

**Runtime 和业务插件互相不能直接依赖实现类。**

Runtime 只认识接口。

Plugin 只认识 SPI。

# 二、阶段一建议拆成 9 个模块

我建议你们从项目结构上就物理拆开，而不是代码都放一个 `core` 目录。

| 模块                     | 职责                                       | 是否允许依赖业务 |
| ---------------------- | ---------------------------------------- | -------: |
| `harness-contracts`    | Request / Context / Result / Error 等公共协议 |        ❌ |
| `harness-spi`          | AgentSPI / ToolSPI / Plugin 定义           |        ❌ |
| `harness-registry`     | 能力注册、查询、解析                               |        ❌ |
| `harness-policy`       | 调用前后的权限/约束决策                             |        ❌ |
| `harness-trace`        | Trace / Span / Event                     |        ❌ |
| `harness-runtime`      | 一次 Invocation 的执行生命周期                    |        ❌ |
| `harness-plugin-local` | 本地插件加载和注册                                |        ❌ |
| `harness-bootstrap`    | 组装各模块、启动 Runtime                         |        ❌ |
| `plugins/*`            | 实际业务 Agent / Tool                        |        ✅ |

推荐项目结构：

```text
harness-agent/
│
├── harness-contracts/
│
├── harness-spi/
│
├── harness-registry/
│
├── harness-policy/
│
├── harness-trace/
│
├── harness-runtime/
│
├── harness-plugin-local/
│
├── harness-bootstrap/
│
├── plugins/
│   ├── echo-agent/
│   ├── calculator-tool/
│   └── mock-finance-agent/
│
└── tests/
    ├── contract-tests/
    ├── integration-tests/
    └── plugin-tests/
```

如果你们后面确定是 Go / Java / Python，可以再映射成具体 package/module。

# 三、第一块先做 Contracts

这个应该是**第一个冻结的模块**。

因为后面几乎所有模块都依赖它。

阶段一只定义最少几个核心对象。

## 1. Request

Request 不应该出现：

```text
FinanceQuestion
SQLQuestion
RiskQuestion
```

这种业务类型。

应该保持完全通用。

例如：

```text
Request
├── request_id
├── session_id
├── tenant_id
├── user
├── input
├── metadata
├── target
└── options
```

概念上可以是：

```text
Request {
    id
    session_id

    input {
        type
        content
    }

    target {
        capability?
        plugin?
    }

    metadata: Map<String, Any>

    options {
        timeout
        trace
    }
}
```

其中：

```text
target = null
```

代表后面可以由 Router 决定。

阶段一为了简单，可以要求：

```text
target.capability
```

必须指定。

例如：

```json
{
  "input": {
    "type": "text",
    "content": "查询今天收入"
  },
  "target": {
    "capability": "finance.query"
  }
}
```

这样阶段一完全不用做 Planner。

---

# 四、Context 一定和 Request 分开

这是很重要的设计。

不要：

```text
Request
  +
Runtime Context
  +
User Context
  +
Trace Context
```

全部塞成一个超级对象。

我建议：

```text
Request
```

代表**用户传进来的东西**。

而：

```text
Context
```

代表**Harness 执行期间的环境**。

例如：

```text
InvocationContext
├── request
├── identity
├── tenant
├── deadline
├── attributes
├── trace_context
└── cancellation
```

阶段一 Context 不要做 Memory。

也不要让插件自己随便写 Context。

最好区分：

```text
Immutable Context
+
Execution State
```

也就是说：

```text
Context = 只读
State   = 本次执行可变
```

否则后面并行 Agent 一来，非常容易出现共享状态污染。

---

# 五、SPI 是整个阶段一最重要的模块

这里建议不要设计成一个万能：

```text
Plugin.execute()
```

否则以后 Agent 和 Tool 很难演进。

至少分：

```text
Capability
Agent
Tool
```

三个概念。

其中 Capability 是统一抽象。

例如：

```text
Capability
├── id
├── name
├── type
├── version
├── input_schema
├── output_schema
├── tags
└── metadata
```

Agent SPI：

```text
Agent {
    descriptor()

    invoke(
        AgentRequest,
        InvocationContext
    ) -> AgentResult
}
```

Tool SPI：

```text
Tool {
    descriptor()

    execute(
        ToolRequest,
        InvocationContext
    ) -> ToolResult
}
```

这里注意一个原则：

> **Agent 和 Tool 可以共享 Descriptor / Result / Error，但不要为了统一而强行变成完全一样的执行语义。**

因为后面 Agent 可能会：

```text
Agent
 ├─ 调 Tool
 ├─ 调 Agent
 ├─ 多轮推理
 └─ Stream
```

而 Tool 理想情况下是：

```text
Input → deterministic operation → Output
```

---

# 六、Registry 不只是一个 Map

阶段一可以用内存实现：

```text
Map<CapabilityId, Provider>
```

但是接口要提前设计正确。

不要让 Runtime：

```text
registry.getAgent("xxx")
```

更建议：

```text
registry.resolve(query)
```

例如：

```text
CapabilityQuery {
    id?
    type?
    tags?
    version?
}
```

返回：

```text
ResolvedCapability {
    descriptor
    provider
}
```

阶段一 Registry 至少提供：

```text
register()
unregister()
get()
list()
resolve()
```

以后可以自然演进到：

```text
多个 Provider
版本选择
健康状态
负载均衡
Remote Agent
MCP
HTTP Tool
```

但阶段一全部不用实现。

---

# 七、本地插件加载单独做模块

这里特别建议和 Registry 分开。

Registry 的职责是：

> **我有哪些 Capability？**

Plugin Loader 的职责是：

> **Capability 从哪里来？**

这是两个概念。

所以：

```text
LocalPluginLoader
        │
        │ discover
        ▼
     Plugin
        │
        │ capabilities()
        ▼
     Registry
```

建议定义：

```text
Plugin {
    manifest()
    capabilities()
    initialize()
    shutdown()
}
```

阶段一生命周期可以非常简单：

```text
DISCOVERED
   ↓
INITIALIZED
   ↓
REGISTERED
   ↓
ACTIVE
   ↓
STOPPED
```

Plugin Manifest：

```text
PluginManifest
├── plugin_id
├── name
├── version
├── sdk_version
├── capabilities[]
└── metadata
```

阶段一只实现：

```text
LocalPluginProvider
```

未来：

```text
LocalPluginProvider
RemotePluginProvider
MCPPluginProvider
HTTPPluginProvider
ContainerPluginProvider
```

Runtime 不需要变化。

# 八、Policy 必须是独立执行链

这一块不要写在 Runtime 里：

```text
if user.xxx:
   deny
```

否则后面会越来越耦合。

设计成：

```text
PolicyEngine
      │
      ▼
Policy[]
```

Invocation 可以经历：

```text
Request
  ↓
PRE_ROUTE policy
  ↓
Registry.resolve
  ↓
PRE_EXECUTE policy
  ↓
Agent / Tool
  ↓
POST_EXECUTE policy
  ↓
Result
```

阶段一其实只做：

```text
PRE_EXECUTE
```

都可以。

接口：

```text
Policy {
    evaluate(PolicyContext) -> PolicyDecision
}
```

返回：

```text
PolicyDecision
├── ALLOW
├── DENY
└── constraints
```

以后可以支持：

```text
ALLOW
DENY
REQUIRE_APPROVAL
MODIFY
RATE_LIMIT
DEGRADE
```

但是阶段一不要做复杂。

可以先做三个简单 Policy：

```text
AllowAllPolicy
TenantPolicy
CapabilityPermissionPolicy
```

# 九、Trace 不应该写死 OpenTelemetry

建议你们一开始就：

```text
Harness
   │
   ▼
Trace SPI
   │
   ├── ConsoleTracer
   └── OTelTracer
```

而不是 Runtime 到处：

```text
otel.startSpan()
```

设计：

```text
Tracer
├── startSpan()
├── addEvent()
└── endSpan()
```

Span：

```text
Span
├── trace_id
├── span_id
├── parent_span_id
├── type
├── name
├── start_time
├── end_time
├── attributes
├── status
└── error
```

阶段一最重要的是把 Span 层级设计出来：

```text
REQUEST
└── RUNTIME
    ├── POLICY
    ├── REGISTRY_RESOLVE
    └── CAPABILITY
        └── TOOL / AGENT
```

例如：

```text
request: req-001
│
├── policy.pre_execute
│
├── registry.resolve
│
└── agent.finance-query
     ├── tool.metric-query
     └── tool.sql-executor
```

哪怕阶段一只有 EchoAgent，也应该能看到完整 Trace。

# 十、Runtime 反而应该非常薄

很多团队容易把 Runtime 写成最大的模块。

我建议相反。

Runtime 只负责 Invocation 生命周期：

```text
receive request
      ↓
create context
      ↓
start trace
      ↓
policy
      ↓
registry.resolve
      ↓
invoke capability
      ↓
normalize result
      ↓
trace finish
      ↓
return
```

核心可以非常接近：

```text
HarnessRuntime.invoke(request)
```

伪代码：

```text
context = contextFactory.create(request)

span = tracer.start("request", context)

decision = policyEngine.evaluate(request, context)

if denied:
    return Result.denied()

capability = registry.resolve(request.target)

result = capability.invoke(request, context)

return normalize(result)
```

注意 Runtime **不要负责**：

```text
SQL
RAG
Prompt
LLM
金融指标
数据源
业务异常判断
```

这些全部应该是 Plugin。

# 十一、统一 ResultEnvelope

这个也建议阶段一就定下来。

不要 Agent 返回：

```text
String
```

Tool 返回：

```text
Map
```

另一个 Agent 返回：

```text
CustomDTO
```

Harness 层统一：

```text
ResultEnvelope
├── status
├── output
├── metadata
├── error
└── trace_id
```

例如：

```text
status:
  SUCCESS
  FAILED
  DENIED

output:
  type
  data

metadata:
  provider
  capability
  version
```

以后 Streaming 可以单独：

```text
ResultEvent
```

阶段一不用实现 Streaming。

# 十二、错误体系也单独设计

这是空项目最容易忽略的。

建议至少区分：

```text
HarnessError
├── RequestError
├── RegistryError
├── PolicyError
├── PluginError
├── CapabilityError
└── TimeoutError
```

错误编码不要放业务描述：

```text
FINANCE_SQL_ERROR
```

应该类似：

```text
HARNESS.REQUEST.INVALID
HARNESS.REGISTRY.NOT_FOUND
HARNESS.POLICY.DENIED
HARNESS.PLUGIN.LOAD_FAILED
HARNESS.CAPABILITY.EXECUTION_FAILED
```

业务插件自己的：

```text
PLUGIN.xxx.xxx
```

# 十五、阶段一明确“不做”的东西

我建议你们把这段直接写进 README。

否则非常容易 scope creep。

```text

× LLM Router
× Supervisor
× 多 Agent DAG
× Workflow Engine
× Memory
× RAG
× NL2SQL

× Remote Agent
× Agent-to-Agent
```

> **证明 Harness 能承载任意本地业务 Agent / Tool，而不与业务发生耦合。**

# 十七、最终阶段一的依赖图

我建议最终 dependency graph 控制成：

```text
                   harness-bootstrap
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
 harness-runtime   local-plugin      concrete impl
        │              loader
        │                │
        ▼                ▼
    Registry ◄──────── Plugin
        │
        │
 ┌──────┼───────┐
 ▼      ▼       ▼
Policy Trace   SPI
 │      │       ▲
 └──────┴───────┤
                │
             Contracts
                ▲
                │
       ┌────────┴─────────┐
       │                  │
   Agent Plugin        Tool Plugin
```

更严格一点讲，`Registry / Policy / Trace` 最好也只依赖：

```text
Contracts / SPI
```

而不是相互调用。

它们之间的协作全部由：

```text
Harness Runtime
```

完成。

这实际上就是 **Mediator + Dependency Inversion**。

## 阶段一验收，我会只看 8 件事

1. 新增一个 Agent 是否完全不改 Harness Core。
2. 新增一个 Tool 是否完全不改 Harness Core。
3. 删除一个插件是否不会影响其他插件。
4. Registry 是否不知道具体业务类型。
5. Policy 是否不知道具体插件实现。
6. Trace 是否可以替换 Console / OTel 实现。
7. Runtime 是否只依赖 SPI，而不是 Plugin 实现。
8. 一次请求是否能完整跑通 `Request → Context → Policy → Registry → Capability → Result → Trace`。

如果这 8 条全部成立，**第一阶段的 Harness 基础就已经非常健康了**。

下一阶段再往上加 `Planner / Router / ExecutionPlan / DAG`，你们会发现不需要推翻当前设计，只是多出一个产生和执行 `ExecutionPlan` 的层，这才是第一阶段真正应该追求的结果。
