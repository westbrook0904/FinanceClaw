# FinanceClaw 数据模型与持久化设计

## 1. 存储拓扑

```text
PostgreSQL cluster
├─ financeclaw_app
│  ├─ conversations/messages
│  ├─ summaries/manifests
│  ├─ approvals/audit/outbox
│  └─ artifact metadata
└─ financeclaw_agent
   └─ Agent Server managed resources/checkpoints/store

Redis
└─ Agent Server queue / pubsub

S3-compatible storage
└─ large artifacts, reports, attachments, encrypted prompt snapshots
```

FinanceClaw 不直接读写 `financeclaw_agent` 内部表；Agent Server 不直接写 FinanceClaw 业务表。

## 2. ID 模型

| ID | 范围 | 说明 |
|---|---|---|
| `conversation_id` | 长期 | 产品多轮会话 |
| `turn_id` | 一轮 | 一次用户输入至可见最终回复 |
| `message_id` | 消息 | append-only 消息 |
| `run_id` | 执行 | 一次 Agent/Workflow/Tool Run |
| `thread_id` | LangGraph | checkpoint thread |
| `model_call_id` | 模型 | 一次模型调用 |
| `tool_call_id` | Tool | 一次 Tool 调用 |
| `approval_id` | 审批 | 一次审批对象 |
| `artifact_id` | Artifact | 大内容引用 |

所有 ID 均由受信任应用生成。外部 idempotency key 与实际资源 ID 分开保存。

## 3. Conversation Journal

### 3.1 conversations

核心字段：

```text
conversation_id PK
tenant_id
subject_id
agent_id
agent_profile_version
agent_thread_id
status
created_at
updated_at
```

`agent_id/agent_profile_version` 是部署侧写入的顶层 Agent 可复现 pin，不属于 Conversation 创建请求或公开响应，也不能由用户切换。

必须存在 `(tenant_id, subject_id, conversation_id)` 所有权查询路径。

### 3.2 conversation_turns

```text
turn_id PK
conversation_id FK
run_id UNIQUE
client_idempotency_key
target_type/id/version  # 当前固定为根 agent；后续仅记录内部 delegation 结果
status
created_at/completed_at
```

建议唯一约束：`(tenant_id, subject_id, client_idempotency_key)`，具体范围由 API 约定确定。

### 3.3 conversation_messages

```text
message_id PK
conversation_id FK
turn_id FK
sequence
parent_message_id nullable
role
content JSON/text
content_hash
visible
created_at
```

规则：

- 用户消息与 Assistant 可见消息永久保存且无自动 TTL；
- 重新生成/编辑通过追加和 parent relationship 表达；
- 隐藏推理不保存；
- Tool 大结果不复制到消息表；
- 附件使用 ArtifactReference。

唯一约束：`(conversation_id, sequence, message_id)` 或等价的严格单调顺序方案。

## 4. Summary 与历史检索

### 4.1 conversation_summaries

```text
summary_id PK
conversation_id
level
start_sequence/end_sequence
source_message_ids
summary_content
topics/entities/decisions/open_items
model_profile_version
template_version
content_hash
status
superseded_by
created_at
```

Summary 是派生数据，可以重建。摘要任务必须幂等，不能对同一 source range 静默创建冲突版本。

### 4.2 检索策略

Prompt 构建同时使用：

- 最近原始消息 token window；
- 与当前问题相关的 segment/hierarchical summaries；
- 必要时召回古老原文；
- stable long-term memory。

第一阶段用 PostgreSQL metadata/filter；需要 semantic search 时启用 pgvector。tenant/subject filter 必须在向量检索条件中执行，而不是召回后过滤。

## 5. ModelContextManifest

```text
manifest_id PK
model_call_id UNIQUE
conversation_id/turn_id/run_id
prompt_template_version
agent/model profile versions
recent_message_start/end
summary_ids
memory_ids
historical_message_ids
tool_result_refs
exposed_tool_ids/versions
input_token_count
omission_counts
context_hash
created_at
```

Manifest 永久保存，但不默认复制完整 Prompt。高风险流程可关联加密 Prompt Artifact。

## 6. Long-term Memory

### 6.1 Memory 类型

```text
preference
goal
constraint
decision_note
```

不允许将实时行情、持仓、订单、余额或可重新计算的风险指标写成当前 Memory 事实。

### 6.2 MemoryDraft

LLM 只可提出：

```text
kind
content
evidence_message_ids
```

系统绑定 tenant、subject、namespace、sensitivity、provenance、identity 和生命周期。

### 6.3 生命周期

```text
active → superseded
active → revoked
active/revoked/superseded → deleted
```

变更必须保留关系和 Audit。`valid_until` 只用于真实时间有效性，不作为通用 TTL。

### 6.4 Store 边界

LangGraph Store 保存 namespaced JSON/document 与 search index；`LongTermMemoryService` 在 Store 之前执行：

- trusted scope；
- namespace；
- evidence；
- sensitivity；
- write confirmation；
- conflict/supersede；
- audit。

不再抽象第二套 MemoryProvider SPI。

## 7. Approval

```text
approval_id PK
tenant_id/subject_id
run_id/thread_id/tool_call_id
tool_id/version
arguments_hash
requested_action
allowed_decisions
status
requested_at/decided_at/expires_at
decided_by
decision_reason
```

任何 Tool 参数变化都必须改变 arguments hash，并使已有批准失效。Approval 可过期，与 Conversation 无 TTL 不冲突。

## 8. Financial Audit

AuditRecord 至少保存：

```text
audit_id/event_type/occurred_at
tenant_id/subject_id
conversation_id/turn_id/run_id/tool_call_id
resource_type/resource_id/action/decision
policy_version
evidence_refs
payload_hash
artifact_refs
metadata
```

Audit 是结构化业务事实，不依赖 LangSmith Trace 是否采样或是否到期。

## 9. Artifact

```text
artifact_id PK
tenant_id/subject_id
content_type
storage_uri
content_hash
size_bytes
source_type/source_id
access_policy
encryption_metadata
created_at
```

适用内容：大 Tool Result、报告、表格、附件、受控 Prompt Snapshot。Prompt 与 Conversation 只保存有界摘要和引用。

## 10. Outbox

只在需要可靠通知 Kafka、消息队列或外部服务时使用。Audit/业务变更与 Outbox 在同一 `financeclaw_app` 事务内写入，Publisher 幂等发送并标记状态。

普通进程内协作直接使用函数调用、LangGraph Stream 或 LangSmith，不建设 EventBus。

## 11. 事务与恢复

FinanceClaw 业务数据库与 Agent Server 数据库不做分布式事务。使用以下策略达到最终一致：

1. 用户消息先幂等写 Journal；
2. 使用稳定 run/thread ID 调用 Agent Server；
3. 最终可见回复按 run_id 幂等写入；
4. 写入失败时从 Agent Server run/checkpoint 查询结果并补写；
5. Audit/Outbox 在业务库本地事务内完成；
6. 定期 Reconciler 检查 completed run 与未完成 turn。

## 12. Migration 与 Ownership

- FinanceClaw 表由 SQLAlchemy + Alembic 管理；
- Agent Server 表由 Agent Server 自己 setup/migrate；
- 两者备份、恢复和升级分别演练；
- 业务代码禁止依赖 Agent Server 内部表结构；
- 数据删除请求必须同时协调 Journal、Memory、Artifact、LangSmith 与 Agent Server thread 数据。
