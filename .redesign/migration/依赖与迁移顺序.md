# 依赖与迁移顺序

## 1. 总体策略

迁移采用“先验证框架—建立新执行脊柱—补齐状态与记忆—发布固定工作流—生产加固”的顺序。每一阶段先完成最小纵向链路，再切换调用点并删除对应旧模块。

```text
Stage 0 Framework Spike
        │
        ▼
Stage 1 BFF → Agent Server → Agent/Tool
        │
        ▼
Stage 2 Conversation → Context → Manifest
        │
        ▼
Stage 3 Long-term Memory
        │
        ▼
Stage 4 Published Workflows
        │
        ▼
Stage 5 Security/Evals/Operations → final legacy cleanup
```

Stage 4 可在 Stage 3 后半段并行准备业务图设计，但不得绕过 Stage 1 的安全边界和 Stage 2 的会话/观测基础。

## 2. 依赖方向

目标代码只允许以下依赖方向：

```text
api/bff
  ├── application dispatch/use cases
  │     ├── agents/workflows
  │     │     ├── tools
  │     │     └── context/memory middleware
  │     └── conversation/approval/artifact services
  ├── security/policy
  └── observability/audit

domain/contracts  ← 上述模块均可依赖
infrastructure    → 实现 domain/application ports
```

禁止 Tool、Middleware 或 Graph 反向依赖 FastAPI 请求对象；禁止 domain 依赖 LangSmith、数据库驱动或 Agent Server SDK。

## 3. Stage 0 顺序

1. 创建隔离的 Spike 环境并固定 Python `>=3.13,<3.14`；
2. 锁定 LangChain/LangGraph/LangSmith/Provider/Postgres/Redis 依赖；
3. 跑通 `create_agent` + 一个读工具 + 一个受审批写工具；
4. 验证 checkpointer、Store、interrupt/resume 和 SSE；
5. 验证 Agent Server 的 graph/assistant/thread/run API；
6. 验证 LangSmith 完整 trace、masking、sampling 和 datasets；
7. 记录版本、限制和继续/停止决策。

不通过的关键能力必须在进入 Stage 1 前形成 ADR，不能用大规模自研代码静默绕过。

## 4. Stage 1 顺序

1. 建立 `financeclaw` 新包和 composition root；
2. 定义 `ExecutionContext`、Target、`ToolGovernance`、`ToolDecision`；
3. 实现不可变 `ToolCatalog` 与首批 LangChain `BaseTool`；
4. 实现模型调用、Middleware、retry/fallback 和 `ModelProfile`；
5. 创建顶层 `finance_agent`；
6. 创建固定 `DirectToolGraph`；
7. 接入 BFF 认证、确定性 dispatch 和 Agent Server；
8. 建立 pytest 纵向集成测试与 LangSmith trace；
9. 切换一个真实请求入口；
10. 删除 runtime/registry/selection/spi/plugin-local 及相关框架契约。

切换完成前不实现 Conversation/Memory 的所有高级策略，先确保执行主干正确。

## 5. Stage 2 顺序

1. 创建 conversation、turn、message、summary、manifest、artifact 元数据表；
2. 实现 append-only ConversationJournal 与 thread 映射；
3. 把 LangChain `BaseMessage` 作为运行时消息标准；
4. 实现 ContextBudget 和最近原文窗口；
5. 实现分段/层级摘要与旧消息相关检索；
6. 创建 `ModelContextManifest` 并在每次模型调用保存；
7. 开发/测试环境增加完整最终 Prompt、工具 Schema、模型/工具 I/O 调试日志；
8. 接入 Artifact Store，避免大结果进入 State/Prompt；
9. 完成长会话、重建和重放测试；
10. 删除旧 context runtime 和自研消息/上下文契约。

数据库先加表和双向可读投影，切换读取后再移除旧表/字段；禁止长期双写两个会话事实源。

## 6. Stage 3 顺序

1. 定义 `MemoryDraft`、`MemoryRecord` 和生命周期；
2. 以 `tenant_id + subject_id` 设计 Store namespace；
3. 实现薄 `LongTermMemoryService`；
4. 实现 recall middleware 和独立 token 预算；
5. 实现 propose/confirm/forget 工具和 HITL；
6. 把记忆引用接入 Manifest、LangSmith 和 Audit；
7. 迁移少量可确认的稳定旧记忆；
8. 验证租户隔离、替代、撤销和删除；
9. 切换读取/写入；
10. 删除旧 Memory Runtime、Provider、Gateway、Policy 和 Store 实现。

历史数据迁移不得把缺乏证据、来源不明或明显时效性的记录直接标记为 `active`。

## 7. Stage 4 顺序

1. 从真实业务选择一个固定流程；
2. 定义版本化输入、输出、State 和审批契约；
3. 用 LangGraph 代码实现并编译 StateGraph；
4. 增加幂等、Artifact、checkpoint、interrupt/resume；
5. 注册到 `WorkflowCatalog` 并发布到 Agent Server；
6. BFF 增加确定性 WorkflowTarget 与 run 映射；
7. 建立图结构、故障、恢复和版本测试；
8. 接入 LangSmith 数据集和正式 Audit；
9. 切换对应业务流程；
10. 删除 Planner、PlanDraft、DAG Builder 和旧 execution 残余契约。

第二个 Workflow 只有在第一个完成上线验收后再复制模式，防止过早抽象。

## 8. Stage 5 顺序

1. 分离 development/test/staging/production 配置；
2. 完成 LangSmith datasets、离线实验和在线评测；
3. 完成 OTel、结构化日志、Audit/outbox 和告警；
4. 完成租户隔离、ToolPolicy、Secret、出站和 MCP 安全测试；
5. 完成 Agent Server/PostgreSQL/Redis/Artifact 部署、备份和恢复；
6. 完成负载、成本、长会话和故障注入测试；
7. 灰度切换全部流量并观察 SLO；
8. 删除 trace/events/bootstrap/policy/contracts 等剩余旧框架；
9. 清理构建、CI、镜像、文档和依赖；
10. 生产就绪评审并移除临时 feature flag。

## 9. 数据迁移原则

### 9.1 先扩展、后切换、再收缩

1. 新增兼容的新表/字段；
2. 离线回填并校验计数、哈希和作用域；
3. 新代码读取新结构；
4. 短期观测一致性；
5. 停止旧写入；
6. 删除旧字段或表。

### 9.2 事实源

- 会话原文唯一事实源是业务 ConversationJournal；
- Agent Server checkpoint 是恢复执行状态，不是业务会话主记录；
- 摘要可重建，不是原文替代品；
- 长期记忆是经治理的稳定信息，不是聊天历史副本；
- Audit 永久独立，不依赖 LangSmith trace 保留期。

## 10. 流量切换与临时开关

允许使用短期、明确范围的 feature flag：

- 指定入口从旧链路切到新链路；
- 指定租户或内部用户灰度；
- 控制完整 Prompt 调试日志；
- 控制新 Workflow 版本发布。

每个 flag 必须有所有者、创建日期、删除日期和默认安全值。不得用 flag 长期维持两套 Runtime、两套 Memory 或两套 trace。

## 11. 提交与回滚

### 11.1 提交建议

每个阶段按以下顺序形成可审查提交：

1. contracts/schema；
2. framework integration；
3. vertical slice and tests；
4. traffic switch；
5. legacy deletion；
6. docs/dependency cleanup。

提交中不得混入 IDE、`.DS_Store` 或阶段外文件。

### 11.2 回滚策略

- 应用回滚：重新部署上一已验证版本；
- Workflow 回滚：新请求绑定上一 active version，活动 run 保持原 version；
- 数据库回滚：优先兼容性前滚，必要时执行预先验证的迁移回滚；
- Provider/模型回滚：恢复上一锁定依赖与 ModelProfile；
- 历史代码：从 Git 历史备份分支恢复用于诊断，而非在 `main` 常驻。

## 12. 每阶段统一门禁

每个阶段结束必须满足：

- 新纵向链路有真实场景和自动化测试；
- LangSmith 能看到 Agent/Workflow/Model/Tool/Middleware 调用链；
- 高影响动作有 ToolPolicy、审批和 Audit；
- 数据有明确租户范围与事实源；
- 依赖和运行环境仍符合 Python 3.13 基线；
- `rg` 与构建证明旧包已无生产引用；
- 文档、Schema、测试和实现版本一致；
- 不存在没有删除期限的兼容层或 feature flag。
