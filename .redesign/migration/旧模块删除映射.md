# 旧模块删除映射

## 1. 目的

本文把当前仓库中的自研框架模块映射到目标架构，明确“复用什么、保留什么、何时删除”。迁移原则是先交付一条可验证的新纵向链路，再切换引用并删除旧实现；不建设长期兼容层，也不维持双 Runtime。

已经在此前重构中删除的模块仍列出，用于保存完整决策背景。

## 3. 允许保留的自有能力

下列内容属于 FinanceClaw 的业务边界，不应因为引入框架而删除：

- `ExecutionContext` 与多租户/主体/请求身份绑定；
- `ToolGovernance` 与确定性 `ToolPolicy`；
- 金融数据标准化、质量、来源、`as_of` 和业务降级；
- 永久会话日志、摘要与 `ModelContextManifest`；
- 长期记忆的类型、确认、证据和生命周期治理；
- Workflow 的业务输入输出、版本和审批语义；
- Financial Audit、幂等、制品与合规数据；
- API/BFF 的认证、授权、归属校验和错误契约。

这些能力应保持薄、明确、可测试，不重新包装 LangChain/LangGraph 的 Runtime。

## 4. 删除门槛

一个旧模块只有在以下条件全部满足后才能删除：

1. 新实现存在至少一条真实纵向链路；
2. 所有生产调用点已切换；
3. 数据迁移或历史读取方案已验证；
4. 新旧行为差异已记录在 ADR/实施说明；
5. pytest 与 LangSmith 回归集通过；
6. LangSmith trace、Audit 和必要 OTel 指标可观测；
7. 回滚依赖版本/部署/数据库策略，而不是保留旧 Runtime；
8. 构建和生产镜像不再引用旧包。

## 5. 禁止的迁移方式

- 不新增 `LegacyAdapter` 长期转发到旧 Runtime；
- 不让新 Catalog 继续接受 Capability/Provider/SPI 对象；
- 不在 LangGraph 外再包一层通用 DAG、run scheduler 或 checkpoint；
- 不把旧 PlanDraft 简化后继续作为默认入口；
- 不同时向旧 Memory Store 与 LangGraph Store 双写；
- 不同时向自研 trace 与 LangSmith 写同构数据；
- 不通过复制旧代码到新包名来完成“迁移”。

## 6. 文件与版本控制注意事项

- 每个删除提交只包含该阶段明确范围，避免混入 IDE、`.DS_Store` 或用户本地改动；
- 删除前用 `rg` 确认生产引用、测试引用和文档引用；
- 更新锁文件、包配置、镜像和 CI，确保旧依赖真正消失；
- 历史实现通过 Git 历史备份分支保留，不在 `main` 留死代码；
- `.design` 作为历史讨论保留，最终实现以 `.redesign` 为准。
