# FinanceClaw 架构决议汇总

状态：RD-001～RD-030 为既有 Accepted 基线；RD-031 确认 Stage-8 服务方向，RD-032 确认基础协调优先和自主演进边界；产品发布仍按阶段验收。

本文件将讨论期 ADR 收敛成实现必须遵守的最终决议。编号仅用于本轮 Redesign；已移除的历史
`.design/` 文档可通过 Git 历史追溯。

## RD-001：运行时版本

决定：使用稳定 CPython `>=3.13,<3.14`，通过 lock 文件固定完整依赖树。

原因：LangChain、LangGraph、Agent Server 及其数据库/Provider 生态在 Python 3.13 上有更稳定、完整的验证面；不以使用最新解释器为目标。

## RD-002：默认顶层 Agent

决定：所有产品会话消息都进入默认 `finance_agent`。该 Agent 使用框架原生 ReAct/Tool Calling，决定直接回答、调用 Tool、调用已发布 Workflow，或把有界任务委派给领域 Agent。

Conversation 不接受可由用户选择的 Agent；领域 Agent 是顶层 Agent 的受控委派目标，不拥有根会话。

废弃：LLM Mode Router、FAST/PLAN/REACT 模式选择。

## RD-003：调用指令不是 Target

决定：产品 API 不暴露 `ToolTarget | WorkflowTarget | AgentTarget`。`/tool <id>`、`/workflow <id>`、`/agent <id>` 等用户输入只是顶层 Agent 的调用偏好，不能提供身份、权限、版本或审批结论。

顶层 Agent 必须先确认目标在当前 Catalog/Profile/Policy 下可见，再按 Schema 提取参数。参数完整且有效时使用指定能力；缺失或无效时进入提槽，仅询问缺少的值；目标不可用时明确返回，不静默替换。

内部控制平面可以保留版本化 Target DTO，用于顶层 Agent 已作出决定后的确定性 handoff、运维探针和测试，但必须使用服务身份，且不进入公开 OpenAPI。

## RD-004：Plan 与 Workflow

决定：复杂 `PlanDraft` 退出在线默认链路。重复、可验证、有审批需求的流程发布为版本化 LangGraph Workflow。

允许：Agent 在自身 Loop 中做轻量任务分解或 Todo；它不生成新的可执行 Workflow DAG。

## RD-005：LangChain 模型与 Agent

决定：使用 LangChain `init_chat_model/create_agent`、Provider Integration、Middleware、structured output、retry 和 fallback。

废弃：自研 ModelProvider、模型消息协议、ReAct Runtime、JSON repair 和模型 retry/fallback 执行器。

## RD-006：ModelProfile

决定：保留版本化 ModelProfile 作为配置和数据治理约束。Agent/Workflow 固定 Profile；LLM 不选择模型。

Fallback 候选必须满足相同 data classification、region、egress、Tool Calling 与 structured output 要求。

## RD-007：LangGraph 统一编排

决定：Agent 和确定性 Workflow 统一运行在 LangGraph。StateGraph、Checkpoint、interrupt/resume、RetryPolicy、Streaming 使用框架原生能力。

废弃：自研 DAG、Scheduler、Checkpoint Schema、Resume Kernel。

## RD-008：Agent Server 执行平面

决定：LangGraph Agent Server 作为内部执行平面，负责 assistants、threads、runs、queue、checkpoint、store、streaming 和 cron。

FinanceClaw API/BFF 是唯一公网入口，不重建这些执行能力。

前提：生产部署前完成 license、成本、数据驻留和 egress 评审。

## RD-009：Tool 标准

决定：Tool 统一使用 LangChain `BaseTool`。本地 Tool、MCP Tool 和领域 Tool 均转换为该标准。

废弃：Capability、AgentSPI、ToolSPI、PluginSPI 及第二套 Tool Schema。

## RD-010：Tool Catalog

决定：仅保留启动后不可变的 `Mapping[tool_id, ManagedTool]`，用于稳定身份、版本固定与暴露集合构建。

它不是动态 Registry，不负责 lifecycle、health、selection、retry、fallback 或执行。

## RD-011：Tool Governance

决定：FinanceClaw 保留 side effect、idempotency、risk、scope、approval、egress、sensitivity、retry profile 和 audit level。

LangChain 没有通用金融 Tool RBAC/ABAC；权限规则实现为纯 Policy 函数并通过 Middleware/HITL 执行，不建设通用 Policy Engine。

## RD-012：Provider fallback

决定：模型 fallback 使用 LangChain。具体金融数据 Provider fallback 下沉到对应领域 Service，并返回 provider、as_of、version 和 fallback_used。

废弃：可用于任意 Capability 的通用 1:N Provider Selection。

## RD-013：Direct Tool

决定：产品中的显式 Tool 指令仍由顶层 Agent 接收。指令中含完整 JSON 参数时，由 Middleware 先做 Schema 校验，再约束本轮只调用指定 Tool；缺参时禁止执行并提槽。所有调用仍经过模型可见性过滤和执行时二次授权。

固定 `DirectToolGraph` 只作为内部控制平面适配器，用于确定性 handoff、运维和测试，不是用户绕过顶层 Agent 的产品入口。

## RD-014：Conversation Journal

决定：所有用户消息和 Assistant 可见回复 append-only 永久保存，无自动 TTL。分支和重新生成追加新消息，不覆盖原文。

不保存：模型隐藏推理、Secret、未脱敏的凭证。

## RD-015：Conversation Context

决定：Prompt 使用 token budget 下的混合策略：最近原文窗口、分段/分层摘要、相关历史原文、长期 Memory 与当前 Tool Result。

废弃：ROUTE/PLAN/EXPLORE Context Consumer 和独立 Context Snapshot/Projection Runtime。

## RD-016：Summary

决定：Summary 是带来源范围、message IDs、模型/模板版本和 hash 的派生索引，可重建、可 supersede，但不删除原始对话。

## RD-017：ModelContextManifest

决定：每次 model call 永久保存精简 Manifest，记录使用的消息范围、summary/memory/tool result refs、暴露 Tool、Prompt/Profile 版本、token 和 context hash；默认不复制完整 Prompt。

## RD-018：调试完整 Prompt

决定：development/test 可显式开启完整 Prompt、Tool Schema、模型 I/O 和 Tool I/O 日志及 LangSmith Trace；生产环境禁止误开开发开关并按数据分类脱敏。

## RD-019：短期状态与长期 Memory

决定：LangGraph Checkpointer 管 thread-scoped state；LangGraph Store 管 cross-thread Memory 的存储和检索机制；FinanceClaw `LongTermMemoryService` 管治理语义。

## RD-020：Memory 内容

决定：长期 Memory 只包含 preference、goal、constraint、decision_note。LLM 只能提出简单 MemoryDraft；系统绑定 tenant、subject、identity、sensitivity、provenance 和生命周期。

实时行情、持仓、余额、订单、财务指标和可重新计算的风险结论不得作为当前 Memory 事实。

## RD-021：Memory 生命周期

决定：Memory 使用 active/superseded/revoked/deleted，而不是以 TTL 作为通用清理机制。确有时间有效性的派生内容使用 `valid_until`。

## RD-022：持久化

决定：第一阶段使用 PostgreSQL。采用 Agent Server 时，推荐同一集群中的 `financeclaw_app` 与 `financeclaw_agent` 独立数据库；Redis 供 Agent Server；大内容进入 S3 兼容 Artifact Store；语义检索优先 pgvector。

## RD-023：LangSmith

决定：LangSmith 是 Agent/Workflow/Model/Tool/Middleware 调用链的主观测与评测平台。development/staging/production 使用独立 Project。

LangSmith Trace 不替代 Conversation Journal、Checkpoint 或 Financial Audit。

## RD-024：OpenTelemetry

决定：OpenTelemetry 只补充 FastAPI、PostgreSQL、Redis、外部 HTTP 等基础设施 Trace/Metrics，通过 run_id 与 LangSmith 关联。

## RD-025：Financial Audit

决定：Tool 决策、审批、金融 Tool 执行、Memory 变更和 Workflow 生命周期使用结构化 AuditRecord 永久保存。Trace/EventBus 不能作为业务审计来源。

## RD-026：安全入口

决定：FinanceClaw API/BFF 完成 OIDC/JWT、tenant/subject、ownership、idempotency 和 Tool Policy；Agent Server 位于内网，使用 service auth。

身份和权限通过可信 Runtime Context 传播，不从 Prompt 或请求 body 的同名字段推导。

## RD-027：凭证

决定：Service Credential 由 Secret Manager/Vault/Kubernetes Secret 管理；Delegated User Credential 只以安全 handle 进入运行时，不能写入 Prompt、State、Journal、Memory、LangSmith metadata 或 Debug Log。

## RD-028：Catalog 与版本

决定：只保留 ToolCatalog、AgentCatalog、WorkflowCatalog、ModelProfileCatalog 等不可变配置映射。Conversation 在内部固定顶层 AgentProfile 版本以保证可复现，但 API 不允许选择或返回该配置；Workflow 固定自身及 Tool/Profile 版本，领域 Agent 委派固定被解析的 Profile 版本。

## RD-029：评测

决定：pytest 负责确定性与集成测试；LangSmith 负责 Dataset、Experiment、回归、线上 Evaluator 与人工反馈。Prompt、模型、Tool、Middleware、Summary 或 Workflow 变化必须跑回归。

## RD-030：迁移策略

决定：采用垂直切片替换。新链路通过验收后直接删除对应旧模块，不长期维护双 Runtime 或兼容层。

## RD-031：Coordinator Service 与共享业务数据库

方向确认日期：2026-09-08。详细设计和发布状态见
[Stage 8 修订方案](./stages/Stage-8-Background-Run-Coordination-实施方案.md)；本决议不代表功能已实现。

决定：

- 新增可独立部署的 Coordinator Service，包含 Webhook Ingress 与 Coordinator Worker；
  统一负责已受理任务的首次提交、委派、交互恢复、子结果交付、取消确认和后台核对。
- LangGraph Run Webhook 是首期正式接入面，事件优先唤醒；回调覆盖不足或丢失由后台观察补偿。
  Delegation 使用独立的结构化请求与结果契约，首期由原生 interrupt/resume 承载。
- BFF 与 Coordinator 暂时使用同一个 `financeclaw_app` 数据库，允许通过明确仓储／应用接口
  组合受理、交互和完成事务。BFF 可持久化受理依据与命令，后续远程执行权只属于 Coordinator。
- 协调协议预留多 Agent backend，由有限 Adapter 适配任务边界。首期仍使用 LangGraph，
  不替换其模型／Graph 运行时，不复制 checkpoint，不引入动态 Plugin／Provider Registry。
- PostgreSQL 保存持久协调责任，coordination 自行实现基础推进；后续增强直接在该包内演进，
  见 RD-032。

与既有决议的关系：RD-007／RD-008 继续约束当前 LangGraph 执行平面，Stage 8 将跨 Run
的业务协调从 BFF 迁出，并预留其他 backend；RD-022 的业务／backend 数据隔离保留，
BFF 与 Coordinator 共用业务数据库；RD-026 的用户安全入口保持不变，Coordinator Webhook
是受认证的内部入口。未来真实跨 backend 委派按独立能力与发布验证开放。

共享数据库意味着数据层与迁移存在有意耦合，不能同时宣称各服务可任意独立升级或无成本分库。
受理、推进和领域写入规则必须有明确入口，不能以共享数据库为由任意跨表更新。

## RD-032：Stage-8 采用 PostgreSQL Worker

状态：Accepted；日期：2026-09-08。用户确认：先具备基础能力，后续增强直接在 coordination
实现，不引入 Temporal。实现证据见 [Stage-8 实施与验证](./stages/Stage-8-实施与验证.md)。

决定：以 PostgreSQL 持久化 Inbox 和到期责任，Coordinator Worker 执行有界推进。
基础闭环包括首次提交、Webhook 唤醒、串行委派、交互恢复、原子结果和断连后的继续执行。
租约与业务 operation 领取分开，claimed／uncertain 不随租约或进程超时而重新发送。

边界：BFF 负责受理与只读展示；Coordinator 负责跨 Run 协调；AgentServer 负责原生 Graph／
模型执行。保留 Backend Adapter 作为未来多 Agent backend 的边界，不设计通用调度框架。
本轮移除 Temporal 实验代码、依赖和桥接／回放分支，后续不以重新引入它作为增强路线。

演进：按实际需要在 coordination 内增加续租、退避、并发控制、租户公平性、故障诊断和监控。
授权、固定发布、操作日志、Delegation／Continuation 与 Journal 一致性属于基础正确性。
通知交付按 8B 扩展，生产迁移与容量按 8C 验证。

当前 8.0 验证已使用真实 PostgreSQL、LangGraph HTTP API 和独立 OS Worker；正式表迁移、
产品入口接线及目标 Agent Server 部署验收属于 8A。
