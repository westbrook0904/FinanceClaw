## 目标与实施顺序

1. 将按摘要解析发布时的 legacy/v2/v3 探测与基础清单读取合并为一条 `LEFT JOIN` 查询。主记录和基础记录都来自不可变发布表，最多各一条；不新增表、索引、缓存或回退。
2. 用类型化的存储结果区分三种物理格式。继续按“主清单摘要、主清单语义、基础清单摘要、执行计划”的原顺序验证；坏基础清单不能遮蔽主清单的 runtime 或 manifest 错误。全局默认指针、legacy 定义登记回读和全局激活保留严格 legacy 入口；Agent 根使用聚合查询。
3. 新增真实 PostgreSQL 测试，验证一次物理执行、格式解析、损坏拒绝、owner 身份和计划限制。保留预算测试中实时门禁、扣额、回放和事务回滚断言，仅调整发布查询计数。
4. 重跑整轮场景及相关回归，比较精确的发布查询和非发布业务模板。轮询、过期扫描和心跳单列，整轮总数和耗时不作硬性下降断言。
5. 归档输入指纹、原始报告、JAR 和前后对比，再同步 README 并形成下一阶段本地提交。

## 实现边界

`ReleaseMapper.getStoredRelease` 按主清单的 `release_hash` 读取，以 JSON 字段 `baseReleaseHash` 自关联基础记录。格式分派由持久化的 `manifest_format` 决定，不尝试多个解码器。`StoredRelease` 分别保存 legacy、v2、v3 正文和基础身份，服务层继续验证原始正文，不能用已裁剪的执行配置替代哈希依据。

`LEFT JOIN` 保留基础缺失或错格式的主记录；主清单先验证摘要和 manifest/runtime，再拒绝无效基础。基础解码错误只暂记不可用，避免提前覆盖外层错误码。v3 最后仍按基础配置验证预算、能力和 scope，并返回计划中的收窄投影。数据库优化器的实际扫描方式由 PostgreSQL 决定，本阶段只证明一次 JDBC 执行，不宣称测得固定数量的索引访问。

全局默认指针、legacy 定义登记回读及全局激活仍走严格 legacy 查询；Agent 根的登记回读、激活和指针校验改用聚合查询，基础格式限制保持。未知摘要不能回退到 current；基础不是 legacy 时不能递归解析。每次 `resolve` 都重新查询，没有进程缓存；执行入口继续检查 Turn 的 owner、Agent 与冻结发布身份，后续 grant、隐私和 lease/fence 检查也未减少。

发布 hash、JSON 格式及 `RuntimeArtifacts` 规则未改，但生产 class 的变化会改变实际运行工件指纹。旧 v3 正文可解析不代表可在新工件执行，仍须通过原有 `requireCompatible` 检查；本阶段不会自动改写旧计划或移动进行中的 Turn。
